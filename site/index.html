Moodle local plugin

One Moodle operation surface for REST, MCP, and a Node CLI.

The project provides a secure Moodle plugin design where the CLI talks directly to Moodle REST, MCP is a parallel interface, and all behavior is implemented through Moodle core APIs.

For installers

Install the plugin on a standard Moodle server.

The plugin is installed as a standard Moodle local plugin. The component is local_moodlia and the folder name is moodlia. Docker is only a development/staging deployment variant, not a runtime requirement.

Standard target paths

Packaged folder
moodlia
Moodle plugin path
/var/www/html/local/moodlia
Upgrade root
/var/www/html

Replace /var/www/html with the real Moodle root that contains admin/cli.

Standard server commands

cp -a moodlia /var/www/html/local/moodlia
cd /var/www/html
php admin/cli/upgrade.php --non-interactive
php admin/cli/purge_caches.php

Development variant

Docker deployment for the configured staging target

The repository can also print or run Docker-oriented commands when DEPLOY_MODE=docker. This is useful for the development server where Moodle lives inside a container. 

sudo docker cp /tmp/moodlia moodle:/var/www/html/public/local/moodlia
sudo docker exec -w /var/www/html moodle php admin/cli/upgrade.php --non-interactive
sudo docker exec -w /var/www/html moodle php admin/cli/purge_caches.php

For maintainers

Technical model

REST, MCP, and the Node CLI expose one shared operation layer. Browser tests verify the resulting Moodle-visible state without requiring a custom plugin UI.

01

Node CLI

Runs outside Moodle and calls REST functions directly using the Moodle token.

02

REST API

Uses Moodle External API classes with typed parameters and return definitions.

03

MCP

Exposes the same canonical operation names through /local/moodlia/mcp.php, tools/list, and tools/call.

04

Operation layer

Validates context, checks capabilities, and calls Moodle core APIs.

Request flow

  1. CLI or web client
  2. REST/MCP adapter
  3. Operation dispatcher
  4. Moodle context and capability checks
  5. Moodle core API

Security baseline

Built for Moodle standards first.

The plugin is intentionally stateless in its first version. It manages Moodle data through Moodle APIs and does not introduce private storage.

External functions

  • Declare functions in db/services.php.
  • Use execute_parameters() and execute_returns().
  • Call validate_parameters() before using input.
  • Call validate_context() before capability checks.

Permissions

  • Use Moodle contexts for every operation.
  • Use require_capability() for protected reads and writes.
  • Use require_login() for Moodle pages.
  • Use confirm_sesskey() for future POST actions.

Data handling

  • No direct SQL for course, module, enrolment, file, question, or user behavior.
  • No plugin-owned Moodle tables in the first implementation.
  • No secrets in logs or browser output.
  • Privacy API uses null_provider while no personal data is stored.
